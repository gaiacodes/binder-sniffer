Binder Sniffer · interview talking points

Presenting This Project

What to say, in order, with the lines that land.

Lead with what it does and why it's hard, not with code. Show you understand the system (binder, the sandbox), made deliberate engineering choices, and know the limits of your own work.

1. The 30-second pitch

"I built a tool that intercepts Android's binder IPC from inside an app, captures the notification a system call carries, and decodes the raw Parcel bytes back into the title and text. It works by hot-patching one function pointer in the app's own linker table, so every binder ioctl passes through my code first — then I forward it so the app never notices."

  • One sentence on what: sniff + decode one app's binder traffic.
  • One sentence on how: GOT patch of ioctl in libbinder, then decode the Parcel.
  • One sentence on the payoff: title/text printed live to logcat, non-destructively.

2. Why it's interesting (the framing)

  • Binder is the single chokepoint for almost all Android IPC — everything funnels through one ioctl on /dev/binder. Hook that and you see everything.
  • It touches the whole stack: ELF/dynamic linking, kernel IPC, serialization formats, and the app sandbox / SELinux security model.
  • It's a real reverse-engineering workflow: capture ground-truth bytes first, then build a decoder to match them — not guess from docs.

3. Architecture in two halves

  • Capture (live, in the app): an injector loads my .so; its constructor patches libbinder's ioctl GOT slot to my function; I filter BINDER_WRITE_READ, walk the command stream, find the notification transaction, and follow the pointer to its Parcel.
  • Decode (pure C, no I/O): a cursor over the Parcel reads the interface token, the AIDL arguments in order, then recovers android.title/android.text from the extras Bundle.
  • Key line: "The same decoder runs live on-device and offline on my Mac against a saved capture." That separation is the design.

4. Technical highlights to name-drop

  • GOT/PLT hooking over inline hooking: flip one pointer, no instruction rewriting, fully reversible. Had to mprotect past RELRO to write the slot.
  • Walking ELF by hand: dl_iterate_phdr → PT_DYNAMIC → DT_JMPREL/SYMTAB/STRTAB to find the ioctl relocation. Shows I understand how dynamic linking actually resolves symbols.
  • Parcel wire format: length-prefixed UTF-16 String16, 4-byte alignment, the 'SYST' interface-token header, type-tagged Bundle values (VAL_STRING vs VAL_CHARSEQUENCE).
  • Command-stream stepping: each binder command encodes its payload size in the code itself (_IOC_SIZE), so I step the stream with no lookup table.
  • Safety: the decoder is read-only and stateless, so it's safe on the binder thread; logging goes to logd over a socket, so it can't re-enter the hook.

5. Decisions & tradeoffs (shows judgment)

  • Fixture-first methodology: captured a real 2,348-byte Parcel, verified the layout from the hex, then wrote the decoder to match — rather than trusting docs that drift by Android version.
  • One deliberate shortcut: instead of parsing the whole Notification object field-by-field (version-fragile), I scan for the android.title/android.text keys and decode the value structurally. I can name this as a conscious rigor-vs-simplicity trade.
  • Realtime over file dump: started by writing captures to a file to build the decoder offline, then inlined the decode once it worked — so the final tool logs live with no disk I/O.

6. The security framing (root vs. not)

  • "Root isn't needed to hook and decode binder — it's needed to break into another app's process to do it." That one line shows you understand the threat model.
  • In your own app: GOT patch + decode run on a stock phone, no root — you own that memory.
  • Injecting into a different app needs root + permissive SELinux, because the app sandbox (UID isolation) and SELinux exist to stop exactly that. This is why Frida needs root for the same job.

7. What I'd do next (forward-looking)

  • Walk the full Notification parcelable in order instead of the keyed-scan shortcut.
  • Confirm the VAL_CHARSEQUENCE branch against a real styled-text capture.
  • Write my own injector (currently reusing a proven one) and a reentrancy guard for heavier hooks.
  • Generalize: a header-decode + hexdump fallback for non-notification transactions.

8. Likely questions — crisp answers

"Why hook ioctl and not something higher-level?"
It's the one syscall all binder traffic funnels through, so one hook catches every transaction regardless of which service or method.
"Does this work on a normal phone?"
In your own app, yes, no root. Against another app, no — that crosses the sandbox and needs root + permissive SELinux.
"How do you not crash the app?"
I always forward to the real ioctl; the decoder is read-only and bounds-checked with a latching error flag, so a malformed Parcel yields empty output, never a crash.
"How did you know the Parcel layout?"
I captured a real one and read the hex, then cross-checked against AOSP (Parcel.cpp, Notification.java) — fixture first, docs second.

Close with: "It's a small tool, but it made me learn how Android IPC, dynamic linking, and the app sandbox actually fit together — end to end."
