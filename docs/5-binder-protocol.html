How the Binder Protocol Works

What actually travels through ioctl(/dev/binder) — the layer the sniffer sits on.

Binder is a request/response protocol spoken between a process and the kernel driver. Userspace never talks to another process directly — it exchanges little command packets with the driver, and the driver relays a transaction into the other process. Everything below is those packets.

1. The model: three parties, one copy

A binder call has three participants: a client, a server, and the kernel driver that brokers between them. The client never names a process or address — it names an object by a small integer handle, and the driver knows which process owns it.

Each process mmaps /dev/binder once at startup, giving the kernel a buffer it can write incoming transactions into. When a transaction is sent, the driver does a single copy: from the sender's data buffer straight into the receiver's mapped region. No double buffering, no serialization in the kernel — the driver treats the payload as opaque bytes (that payload is the Parcel).

2. One synchronous call, end to end

CLIENT process KERNEL (binder driver) SERVER process ────────────── ────────────────────── ────────────── ioctl(fd, BINDER_WRITE_READ) write: BC_TRANSACTION ─────► find target by handle copy payload into server's mapped buffer, queue it read: BR_TRANSACTION_COMPLETE ◄── (your send was accepted) ...client blocks in read... wake a server thread ──────────► ioctl(... ) read returns BR_TRANSACTION (code, buffer) → dispatch to onTransact() → do the work ◄─────────────────────────────── write: BC_REPLY read returns: BR_REPLY ◄────── copy reply into client buffer → unblock, read the result write: BC_FREE_BUFFER (release the mapped bytes)

A one-way (async) call sets the TF_ONE_WAY flag: the driver queues it and returns immediately, there is no BR_REPLY, and the client never blocks. Our target, enqueueNotificationWithTag, is a normal synchronous call.

3. The transport: BINDER_WRITE_READ

One ioctl command does nearly everything: BINDER_WRITE_READ. Its argument bundles an outgoing command buffer and space for incoming ones, so a single syscall both sends and receives.

fieldmeaning
write_sizebytes of commands to send to the driver
write_consumedhow many the driver processed (it updates this)
write_bufferpointer to the outgoing command stream (the part we read)
read_sizecapacity for commands coming back
read_consumedhow many bytes the driver returned
read_bufferpointer to where returns (BR_*) are written

The sniffer only looks at write_buffer/write_size — the commands leaving the app. The reply side (read_buffer) we leave alone.

4. The command stream: BC out, BR back

Both buffers are packed streams of commands. Each command is a 32-bit code, optionally followed by a fixed payload. The code is defined with the kernel's _IOW/_IOWR macros, so its size field (bits 16–29) encodes the payload length — which is exactly how you step from one command to the next without a lookup table (BC_PAYLOAD_SIZE in the hook).

BC_* — app → driver
BC_TRANSACTION start a call
BC_REPLY answer one
BC_TRANSACTION_SG + scatter-gather size
BC_FREE_BUFFER release received bytes
BC_ENTER_LOOPER this thread joins the pool
BC_ACQUIRE / BC_RELEASE refcount a handle
BR_* — driver → app
BR_TRANSACTION an incoming call
BR_REPLY your call's result
BR_TRANSACTION_COMPLETE send accepted
BR_SPAWN_LOOPER make another thread
BR_NOOP filler
BR_DEAD_BINDER target died

5. Inside a transaction

A BC_TRANSACTION's payload is a binder_transaction_data. It is the envelope; the method arguments live behind a pointer in it, not inline.

fieldmeaning
target.handlewhich object the call is for (an index, not an address)
codewhich method — the AIDL transaction code (ours is 7)
flagse.g. TF_ONE_WAY for async, accept-fds
sender_pid / euidfilled in by the kernel — the caller's identity the server can trust
data_sizelength of the Parcel payload
offsets_sizelength of the offsets array (see below)
data.ptr.bufferpointer to the Parcel bytes — what the sniffer decodes
data.ptr.offsetspointer to an array marking embedded binder objects

The data buffer is a Parcel — the flat argument bytes. The offsets array lists positions inside that buffer where a flat_binder_object sits (a passed binder reference or a file descriptor). The kernel walks those offsets and translates each one as it crosses the boundary: a local object (BINDER_TYPE_BINDER) in the sender becomes a handle (BINDER_TYPE_HANDLE) in the receiver. The sniffer ignores the offsets — notification title/text are plain Parcel data, not binder objects.

6. Addressing: handles and the context manager

Objects are named by 32-bit handles that are per-process — the same server is handle 11 in one client and 23 in another; the driver maps each to the real object. There is one well-known handle: handle 0 is the context manager (servicemanager). To reach any other service, a client sends a transaction to handle 0 asking for a service by name; servicemanager replies with a flat_binder_object, and the kernel hands the client a fresh handle for it. That is how INotificationManager gets a handle in the first place.

7. Threads and buffer ownership

Each process runs a binder thread pool. A thread announces itself with BC_ENTER_LOOPER/BC_REGISTER_LOOPER and then blocks in the read side of ioctl waiting for work; when load rises the driver sends BR_SPAWN_LOOPER to ask userspace for another. This is why the sniffer sees BINDER_WRITE_READ on several threads, and why the decoder has to be safe to run on any of them.

When a transaction is delivered, the payload lives in the receiver's mapped region and the receiver owns those bytes until it returns them with BC_FREE_BUFFER. That is the one-copy design's bookkeeping.

What the sniffer actually touches

Of this whole protocol we read exactly one slice: in a BINDER_WRITE_READ's write buffer, each BC_TRANSACTION, and from its binder_transaction_data the code and data.ptr.buffer/data_size. We never decode BR_ returns, replies, offsets, handles, or the refcount commands — they're part of the protocol but not part of the message we're after.
